# Сценарий 1. Ограничение частоты запросов: фиксированное окно

Тест: `src/test/java/io/github/olaaa/redispatternslab/scenario/Scenario1FixedWindowTest.java`.
Ограничители: `RedisFixedWindowRateLimiter` (бин, счётчик в Redis) и `LocalFixedWindowRateLimiter` (для сравнения, счётчик в памяти реплики). Фильтр: `RateLimitWebFilter` на `/products/**`. Настройки: `rate-limit.limit` = 10, `rate-limit.window` = 1 секунда.
Ручная проверка: `http/01-fixed-window.http` и команды `curl` ниже.

Коротко:

- **Что делаем.** Один клиент может сделать не больше 10 запросов к каталогу в секунду — на всех репликах вместе. Лишние запросы получают ответ 429 Too Many Requests.
- **Почему в Redis.** Счётчик в памяти реплики видит только её запросы: три реплики с лимитом 10 пропустят 30.
- **Как.** Фиксированное окно: на каждую секунду и каждого клиента — счётчик в Redis, каждый запрос увеличивает его командой `INCR`, у счётчика срок жизни — длина окна.
- **Слабое место.** На границе двух окон клиент успевает сделать вдвое больше лимита. Как это исправить — сценарий 2.

## Зачем ограничивать частоту

Один клиент может завалить сервис запросами: мобильное приложение с ошибкой повторяет запрос в цикле, партнёр запускает выгрузку каталога без пауз, кто-то перебирает товары скриптом. Запросы этого клиента нагружают базу, и медленнее отвечают всем остальным.

Ограничение частоты (rate limiting) задаёт каждому клиенту предел: не больше N запросов за период. Запрос сверх предела не обрабатывается, клиент получает ответ 429. RFC 6585: «код 429 означает, что пользователь отправил слишком много запросов за заданное время»; ответ может содержать заголовок `Retry-After` — через сколько повторить.

Кто такой «клиент», решает сервис. Здесь — значение заголовка `X-Client-Id`, без него — адрес клиента. В настоящем API это обычно ключ API или идентификатор пользователя из токена.

## Почему не в памяти реплики

Проще всего считать запросы в памяти: `ConcurrentHashMap` от клиента к счётчику. Так устроен `LocalFixedWindowRateLimiter`. Внутри одной реплики он считает верно, но реплик несколько, и запросы клиента балансировщик раскидывает по ним. У каждой реплики свой счётчик, и каждая пропускает по 10.

Тест `localLimiterOnEachReplicaLetsThroughLimitTimesReplicas`: 30 запросов одного клиента по очереди через три реплики — пропущены все 30. Лимит фактически умножается на число реплик и меняется при масштабировании.

Нужен один счётчик на всех — в Redis.

## Фиксированное окно в Redis

Документация команды `INCR` описывает этот приём как шаблон «ограничитель частоты» (rate limiter): «Шаблон ограничителя частоты — это особый счётчик, который ограничивает частоту выполнения операции. Классический пример — ограничение числа запросов к публичному API». Первый вариант оттуда — счётчик на каждую секунду: ключ — IP-адрес плюс текущее время в секундах, `INCR` и `EXPIRE` внутри `MULTI`/`EXEC`.

`RedisFixedWindowRateLimiter` делает то же:

1. Время режется на окна по секунде. Запрос в 10:00:00.700 попадает в окно, которое началось в 10:00:00.000.
2. Ключ счётчика — клиент плюс начало окна: `rate:fixed:mobile-app:1793527200000`.
3. `INCR` этого ключа возвращает значение после увеличения — номер запроса в окне. Номер не больше 10 — запрос пропускается, больше — 429.
4. При первом запросе в окне ключу ставится срок жизни, равный длине окна. Старые счётчики Redis удаляет сам.

```lua
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
return count
```

**Почему `INCR`.** Увеличение в Redis атомарно: из 100 одновременных запросов каждый получит свой номер от 1 до 100, и пропущено будет ровно 10. Пара «прочитать счётчик, сравнить, записать» отдельными командами пропустила бы больше: два запроса прочитали бы одно и то же значение. Тест `concurrentRequestsNeverExceedLimit` отправляет 100 запросов одновременно и видит ровно 10 пропущенных.

**Почему `INCR` и срок жизни — одним скриптом.** Если отправить их отдельными командами, а процесс упадёт между ними, у ключа не будет срока жизни. Документация Redis про похожий вариант: «В этом коде есть гонка. Если по какой-то причине клиент выполнит INCR, но не выполнит EXPIRE, ключ останется в Redis, пока тот же IP-адрес не появится снова». И способ исправить: «это легко исправить, превратив INCR с необязательным EXPIRE в Lua-скрипт, который отправляется командой EVAL». В шаблоне из документации ключ один на клиента: оставшись без срока жизни, он заблокировал бы клиента навсегда. Здесь у каждого окна свой ключ, поэтому потерянный срок жизни — это утечка памяти: ключ прошлого окна никто не удалит.

**Retry-After.** Отклонённый запрос получает время до конца текущего окна, округлённое вверх до целых секунд: заголовок принимает только целое число секунд.

**Отклонённые запросы тоже засчитываются.** `INCR` выполняется до проверки, поэтому счётчик растёт и на запросах сверх лимита. На решение это не влияет: всё, что больше 10, отклоняется, а в следующем окне счётчик новый.

**Чьи часы.** Окно вычисляет приложение по своим часам (`Clock`), а не Redis. Так тест двигает время без `sleep`. Цена: если часы реплик расходятся, окна у них сдвинуты на это расхождение. Альтернатива — брать время из Redis командой `TIME` внутри скрипта: тогда часы у всех одни. Это вывод, в лаборатории не проверялся.

## Слабое место: граница окон

Окна жёсткие: в 10:00:01.000 счётчик начинается с нуля, сколько бы запросов ни пришло в 10:00:00.999.

```text
        окно 10:00:00 – 10:00:01          окно 10:00:01 – 10:00:02
|-----------------------------|-----------------------------|
                     10 запросов | 10 запросов
                     в 0,900 с    в 1,000 с
```

Тест `windowBoundaryLetsThroughTwiceTheLimit`: часы на 10:00:00.900 — пропущены 10 запросов; часы на 10:00:01.000 — пропущены ещё 10. За 100 мс — 20 запросов, вдвое больше лимита. Для защиты базы от перегрузки этого часто достаточно: в среднем за долгое время клиент всё равно не превысит лимит. Если всплеск на границе недопустим, нужно окно, которое движется вместе со временем, или ведро токенов — сценарий 2.

## Готовые реализации

Здесь алгоритм написан вручную, чтобы было видно, что внутри. В приложениях обычно берут готовое:

- **Bucket4j** — Java-библиотека, по документации «основанная на алгоритме ведра токенов» (token bucket), а не на фиксированном окне. Для нескольких реплик хранит состояние во внешнем хранилище: в Redis через Lettuce, Redisson или Jedis, в распределённых кэшах (Hazelcast, Infinispan и других), в PostgreSQL и других базах. Redis при этом нужен так же, как здесь, — только алгоритм пишет библиотека. Официального стартера Spring Boot нет, есть сторонний `bucket4j-spring-boot-starter`.
- **Spring Cloud Gateway** — фильтр `RequestRateLimiter` с `RedisRateLimiter`: тоже ведро токенов на Redis, при превышении отвечает 429. Ограничение ставится на шлюзе, перед сервисами.
- **Resilience4j `RateLimiter`** считает разрешения в памяти экземпляра — по устройству, документация прямо этого не говорит. Общего лимита на несколько реплик он не даёт.

## Что проверяют тесты

`localLimiterOnEachReplicaLetsThroughLimitTimesReplicas`: три реплики со счётчиком в памяти, 30 запросов по очереди — пропущены все 30.

`redisLimiterSharesCounterAcrossReplicas`: три реплики со счётчиком в Redis — бин и два отдельных экземпляра, — 30 запросов по очереди — пропущено 10.

`concurrentRequestsNeverExceedLimit`: 100 одновременных запросов одного клиента — пропущено ровно 10.

`counterStartsOverInNextWindow`: 10 запросов пропущены, 11-й отклонён с `retryAfter` = 1 секунда — часы стоят на начале окна. Другой клиент проходит: у него свой счётчик. Часы сдвинуты на секунду — запрос снова проходит, осталось 9.

`windowBoundaryLetsThroughTwiceTheLimit`: 20 запросов за 100 мс на границе окон.

`counterKeyExpiresWithItsWindow`: после первого запроса у ключа счётчика срок жизни больше нуля и не больше секунды.

`filterAnswersTooManyRequestsWithRetryAfter`: 10 запросов `GET /products/1` с `X-Client-Id` — 200 и `X-RateLimit-Remaining` от 9 до 0; 11-й — 429 и `Retry-After: 1`; другой клиент — 200.

Тесты двигают часы приложения (`MutableClock`), поэтому окна сменяются без `sleep`. Срок жизни ключей считает сам Redis по своим часам.

## Попробовать вручную

Запустить приложение: `mvn spring-boot:run`. Двенадцать запросов подряд от одного клиента:

```bash
for i in $(seq 12); do
  curl -s -o /dev/null -w '%{http_code} remaining=%header{x-ratelimit-remaining} retry-after=%header{retry-after}\n' \
    -H 'X-Client-Id: mobile-app' localhost:8080/products/1
done
docker compose exec redis redis-cli --scan --pattern 'rate:fixed:*'
```

Результат такого прогона:

```text
200 remaining=9 retry-after=
200 remaining=8 retry-after=
200 remaining=7 retry-after=
200 remaining=6 retry-after=
200 remaining=5 retry-after=
200 remaining=4 retry-after=
200 remaining=3 retry-after=
200 remaining=2 retry-after=
200 remaining=1 retry-after=
200 remaining=0 retry-after=
429 remaining= retry-after=1
429 remaining= retry-after=1
rate:fixed:mobile-app:1793489173000
```

Двенадцать запросов уложились в одну секунду: десять пропущены, два отклонены. Если цикл попадёт на границу секунды, отклонённых не будет — это и есть слабое место фиксированного окна.

В `http/01-fixed-window.http` — те же запросы для IntelliJ HTTP Client.

## Что важно заметить

- Ограничитель частоты на нескольких репликах — это общий счётчик. В памяти реплики лимит умножается на число реплик.
- `INCR` атомарен, поэтому одновременные запросы не проскакивают сверх лимита.
- `INCR` и срок жизни — одной атомарной операцией: Lua-скриптом или `MULTI`/`EXEC`. Иначе счётчики без срока жизни остаются в Redis.
- Фиксированное окно просто и дёшево — один ключ и одна команда на запрос, — но на границе окон пропускает до двойного лимита.

## Как сказать на собеседовании

«Ограничение частоты на нескольких репликах держу в Redis: счётчик в памяти реплики умножает лимит на число реплик. Самый простой вариант — фиксированное окно: ключ "клиент плюс номер окна", каждый запрос — `INCR`, его результат и есть номер запроса в окне; больше лимита — 429 с `Retry-After`. `INCR` атомарен, поэтому одновременные запросы не проскакивают. Срок жизни ставлю в том же Lua-скрипте, что и `INCR`, — иначе при падении между командами ключ останется без срока. Минус — на границе окон клиент успевает сделать до двух лимитов; если это важно, беру скользящее окно или ведро токенов».
