# Сценарий 3. Распределённая блокировка с арендой

Тест: `src/test/java/io/github/olaaa/redispatternslab/scenario/Scenario3LeaseLockTest.java`.
Блокировка: `RedisLock` (ключи `lock:<имя>`). Задача под блокировкой: `CatalogExportJob` — выгрузка каталога партнёру, блокировка `catalog-export`. Партнёр: `PartnerInbox` — считает выгрузки и сколько их шло одновременно. Настройки: `catalog-export.lease` = 10 секунд, `work-duration` = 5 секунд, `renew-every` = 3 секунды.
Ручная проверка: `http/03-lease-lock.http` на двух репликах и команды `redis-cli` ниже.

Коротко:

- **Что делаем.** Выгрузку каталога партнёру запускает каждая реплика, а выполнить её должна одна. Кто выгружает, решает блокировка в Redis.
- **Как взять.** `SET lock:catalog-export <маркер> NX PX <срок>`: ключ создаётся, только если его нет, и сам исчезнет через срок аренды — даже если держатель упал.
- **Как снять.** Только свою: удалить ключ, если в нём мой маркер. Простой `DEL` может удалить чужую блокировку.
- **Долгая работа.** Аренду продлевают, пока работа идёт, — тем же сравнением маркера.
- **Граница.** Если держатель остановился дольше срока аренды, блокировку возьмёт другой, и работать будут двое. Блокировка с арендой не гарантирует, что держатель один. Защита — маркер ограждения, см. раздел «Где аренда не спасает».

## Зачем блокировка

Выгрузка каталога партнёру — задача по расписанию. Расписание есть на каждой реплике, и без договорённости каждая реплика выгрузит каталог: три реплики — три выгрузки, причём одновременно. Тест `withoutLockEveryReplicaExports` это и показывает: три выгрузки, все три одновременно. Партнёр получит три копии, а одновременные выгрузки у него перемешают файлы.

Нужна блокировка, общая для всех реплик: кто взял — выгружает, остальные пропускают этот запуск.

Мартин Клеппман различает две причины брать блокировку — эффективность и корректность. Эффективность: «блокировка избавляет от того, чтобы без нужды делать одну и ту же работу дважды (например, дорогое вычисление)». Корректность: «блокировка не даёт параллельным процессам мешать друг другу и портить состояние системы». Для эффективности редкий второй исполнитель — лишняя работа. Для корректности — испорченные данные, и требования к блокировке тогда строже. У нас второе: перемешанные файлы у партнёра.

## Взять: `SET NX PX` с маркером

Документация Redis даёт для одного экземпляра Redis одну команду:

```text
SET resource_name my_random_value NX PX 30000
```

«Команда создаёт ключ, только если его ещё нет (`NX`), со сроком жизни 30 000 миллисекунд (`PX`). Значение ключа — my_random_value. Оно должно быть уникальным среди всех клиентов и всех запросов блокировки».

- **`NX`** — из одновременных попыток ключ создаст одна, остальные получат отказ. Это и есть взаимное исключение.
- **`PX`** — срок аренды. Держатель упал и не снял блокировку — она освободится сама. Документация называет это свойством «отсутствие взаимоблокировки»: «в конце концов блокировку всегда можно взять, даже если клиент, который её держал, упал или оказался отрезан от сети». Тест `leaseFreesLockWhenHolderDies`: «упавшая» реплика не сняла блокировку, но через срок аренды её взяла другая.
- **Маркер** — случайная строка (`UUID`), своя у каждого взятия. Нужна, чтобы снять и продлить только свою аренду.

В коде:

```java
public Mono<LockHandle> tryAcquire(String name, Duration lease) {
    return Mono.defer(() -> {
        String token = UUID.randomUUID().toString();
        return redis.opsForValue().setIfAbsent(KEY_PREFIX + name, token, lease)
                .filter(Boolean::booleanValue)
                .map(acquired -> new LockHandle(name, token));
    });
}
```

Тест `onlyOneReplicaExportsWhileLockIsHeld`: три реплики одновременно запускают выгрузку — выгрузила одна, остальные две получили `false`, после выгрузки блокировка снята.

## Снять: только свою

Документация Redis: «случайное значение нужно, чтобы снять блокировку безопасно — скриптом, который говорит Redis: удали ключ, только если он есть и в нём ровно то значение, которое я ожидаю».

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

Зачем: «клиент может взять блокировку, застрять в какой-то операции дольше времени действия блокировки — момента, когда ключ истечёт, — а потом снять блокировку, которую уже взял другой клиент. Просто `DEL` небезопасен: клиент может удалить чужую блокировку».

Тест `releaseRemovesOnlyOwnLock` повторяет этот случай:

1. Реплика A взяла блокировку на 200 мс, аренда истекла.
2. Блокировку взяла B.
3. A снимает «свою» блокировку скриптом — скрипт видит в ключе маркер B и ничего не удаляет.
4. A снимает простым `DEL` (`releaseWithoutTokenCheck`) — блокировка B удалена, и её берёт C, хотя B ещё работает.

В Redis 8.4 для этого появилась отдельная команда: `DELEX key IFEQ my_random_value` — удалить, только если значение совпадает. Образ `redis:8-alpine` в лаборатории — Redis 8.10.3, команда в нём есть (проверено ниже, в «Попробовать вручную»). В коде остался скрипт: он работает на любой версии и устроен так же, как продление.

**Снять при любом исходе.** Выгрузка обёрнута в `Mono.usingWhen`: блокировка снимается и после успеха, и после ошибки, и при отмене. Тест `lockIsReleasedWhenExportFails`: партнёр недоступен, выгрузка упала — блокировка снята сразу, следующий запуск её берёт. Без этого блокировка провисела бы до конца аренды.

## Срок аренды и продление

Документация Redis: «время действия блокировки — это срок жизни ключа. Это и время автоматического освобождения, и время, за которое клиент должен выполнить свою операцию, прежде чем блокировку сможет взять другой клиент». И взаимное исключение гарантировано, «только пока клиент, держащий блокировку, заканчивает работу в пределах времени действия блокировки».

Отсюда выбор срока: длиннее обычной работы — но чем длиннее, тем дольше все ждут после падения держателя. Для долгой работы аренду продлевают по ходу: Redis описывает продление как скрипт, «который продлевает срок жизни ключа, если ключ существует и в нём всё ещё то случайное значение, которое клиент записал при взятии блокировки».

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
```

`CatalogExportJob` с `renew-every` продлевает аренду по таймеру, пока выгрузка идёт:

```java
Disposable renewal = Flux.interval(renewEvery)
        .concatMap(tick -> lock.extend(handle, properties.lease()))
        .subscribe();
return export(replica).doFinally(signal -> renewal.dispose());
```

Тест `renewalKeepsLockDuringLongExport`: аренда 300 мс, выгрузка 1 секунда, продление каждые 100 мс. Через 600 мс — вдвое дольше аренды — B пробует взять блокировку и не может.

Но документация предупреждает: «не стоит считать, что блокировка удерживается, пока жив процесс, который её взял».

## Где аренда не спасает

Тест `leaseExpiringDuringLongExportLetsSecondReplicaIn`: аренда 300 мс, выгрузка 1 секунда, продления нет.

1. A взяла блокировку и выгружает.
2. Через 300 мс аренда истекла, A об этом не знает и продолжает.
3. Через 500 мс B берёт блокировку и тоже выгружает: две выгрузки одновременно.
4. A заканчивает и снимает «свою» блокировку — маркер в ключе уже B, скрипт ничего не удаляет. Хотя бы чужую блокировку A не сломала.

Продление эту дыру не закрывает, а сужает. Продлевать перестаёт не только упавший процесс, но и живой: долгая пауза сборки мусора, остановленная виртуальная машина, обрыв сети до Redis. Процесс проснётся и продолжит работу, уверенный, что блокировка его. Клеппман: если пауза сборки мусора длиннее срока аренды и клиент не заметил, что аренда истекла, он «может внести небезопасное изменение». И проверка перед записью не помогает: «эту проблему нельзя исправить, вставив проверку срока блокировки прямо перед записью в хранилище» — пауза может случиться между проверкой и записью.

Вывод: блокировка с арендой даёт «обычно один исполнитель», а не «всегда один». Для эффективности этого хватает. Для корректности нужно, чтобы само хранилище отвергало запись устаревшего держателя, — маркер ограждения (fencing token): номер, который растёт при каждой выдаче блокировки, а хранилище отклоняет запись с номером меньше уже виденного (Клеппман). В лаборатории он не разбирается.

Ещё одно ограничение — это блокировка на одном Redis. Реплика Redis получает данные с задержкой, и если основной узел упал сразу после `SET`, новый основной может не знать о блокировке. ShedLock прямо предупреждает о своём провайдере для Redis: подход «может быть ненадёжен при отказе основного узла Redis». Для нескольких независимых узлов Redis описывает алгоритм Redlock; в лаборатории он не разбирается.

## Готовые реализации

**ShedLock** — библиотека блокировок для задач по расписанию: «ShedLock гарантирует, что ваши задачи по расписанию выполняются не больше одного раза в одно и то же время». Хранилище — база данных, Mongo, Redis и другие; для Redis есть провайдеры на Spring Data Redis (обычный и реактивный), Jedis и Lettuce. `lockAtMostFor` — то же, что срок аренды: «страховка на случай, если узел, выполняющий задачу, упал». `lockAtLeastFor` держит блокировку не меньше заданного времени: очень короткая задача иначе успела бы выполниться ещё раз на реплике, у которой часы чуть отстают. И оговорка: «ShedLock — не полноценный планировщик и никогда им не будет, это просто блокировка». Разобран в отдельном репозитории [shedlock-lab](https://github.com/olaaa/shedlock-lab) — на PostgreSQL и R2DBC.

## Что проверяют тесты

`withoutLockEveryReplicaExports`: три реплики без блокировки — три выгрузки, все одновременно.

`onlyOneReplicaExportsWhileLockIsHeld`: три реплики одновременно — выгрузила одна, блокировка после выгрузки снята.

`lockIsReleasedWhenExportFails`: выгрузка упала — блокировка снята сразу, следующий запуск выгружает.

`leaseFreesLockWhenHolderDies`: держатель не снял блокировку — она освободилась через срок аренды, не раньше.

`releaseRemovesOnlyOwnLock`: скрипт не удаляет чужую блокировку, простой `DEL` удаляет — и блокировку получает третья реплика, пока вторая работает.

`renewalKeepsLockDuringLongExport`: с продлением долгая выгрузка не теряет блокировку.

`leaseExpiringDuringLongExportLetsSecondReplicaIn`: без продления аренда истекла посреди выгрузки, и выгружали двое одновременно.

Сроки аренды в тестах — сотни миллисекунд: истечение считает сам Redis по своим часам, и тест ждёт его через `await`, без `sleep`. При первом прогоне сценария тест поймал ошибку в `CatalogExportJob`: `thenReturn(true)` стоял снаружи `flatMap` и превращал отказ в блокировке — пустой `Mono` — в `true`. Это ловушка `then` из разбора «момент сборки и момент подписки»: `then` не различает «завершился пустым» и «завершился после работы».

Весь набор тестов лаборатории, 20 тестов, прогнан три раза подряд без падений.

## Попробовать вручную

Две реплики в двух терминалах:

```bash
mvn spring-boot:run
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
```

Почти одновременно запустить выгрузку на обеих — она длится 5 секунд:

```bash
curl -s -X POST localhost:8080/lab/reset
curl -s -X POST localhost:8080/lab/catalog-export & curl -s -X POST localhost:8081/lab/catalog-export & sleep 1
docker compose exec redis redis-cli GET lock:catalog-export
docker compose exec redis redis-cli PTTL lock:catalog-export
wait
```

Результат такого прогона:

```text
GET: d4dbd8e3-9e1f-4954-bc18-42ce89ac6659
PTTL: 8779
{"replica":"replica-8080","exported":false}
{"replica":"replica-8081","exported":true}
```

В ключе — маркер реплики 8081, до конца аренды 8,8 секунды: аренда 10 секунд, прошло чуть больше одной. Выгрузила 8081, реплика 8080 получила отказ. После выгрузки ключа нет: блокировка снята, а `GET /lab/partner-inbox` на 8081 показывает одну выгрузку.

`DELEX` в `redis-cli`:

```bash
docker compose exec redis redis-cli SET lock:demo token-a NX PX 60000
docker compose exec redis redis-cli SET lock:demo token-b NX PX 60000
docker compose exec redis redis-cli DELEX lock:demo IFEQ token-b
docker compose exec redis redis-cli DELEX lock:demo IFEQ token-a
```

Первый `SET` — `OK`, второй — пусто: ключ уже есть. `DELEX` с чужим значением — `0`, ключ на месте; со своим — `1`, ключ удалён.

## Что важно заметить

- Взять — `SET NX PX` со случайным маркером; снять и продлить — только при совпадении маркера, атомарно: скриптом или `DELEX`.
- Снимать — при любом исходе работы, иначе блокировка висит до конца аренды.
- Срок аренды освобождает блокировку упавшего держателя, но он же отнимает её у живого, который застрял дольше срока. Продление сужает окно, но не закрывает: остановленный процесс не продлевает.
- Блокировка с арендой годится, когда второй исполнитель — лишняя работа. Если второй исполнитель портит данные, нужен маркер ограждения.

## Как сказать на собеседовании

«Чтобы задачу по расписанию выполняла одна реплика, беру блокировку в Redis: `SET lock:<имя> <случайный маркер> NX PX <срок>`. `NX` даёт одного победителя, срок — освобождение, если держатель упал. Снимаю только свою — скриптом, который сравнивает маркер, или `DELEX ... IFEQ` в Redis 8.4+; простой `DEL` после истечения аренды удалит чужую блокировку. Снимаю при любом исходе, для долгой работы продлеваю тем же сравнением маркера. Но помню: аренда может истечь у живого процесса — пауза сборки мусора, сеть, — и тогда работают двое. Для эффективности это приемлемо, для корректности нужен маркер ограждения, который проверяет само хранилище. Для задач по расписанию в Spring обычно беру ShedLock».
